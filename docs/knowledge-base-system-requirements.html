Overview

概要

不具合報告や問い合わせを知識ベースから検索し、ヒットすれば表示・追記、未ヒットなら新規登録できるシステム。GitLabイシュー限定だった元の設計を土台に、対象knowledge base・LLM・テナントを汎用化する。

全体を規定する前提

外部KB(GitLab / GitHub / Redmine)が知識の正であり、pgvector は検索用インデックスにすぎない。

新規知識はKB側にIssue / チケットとして作成される。この前提から、pgvectorのデータは捨てて再構築できる派生データであること、KB API障害時は新規登録が止まること、ラベルがKBネイティブ機能として使えることが導かれる。他の決定の多くがこれに依存している。

APIトークン等の認証情報はサーバー側DBで管理し、ブラウザには平文で持たせない。ブラウザのlocalStorageはアカウント識別情報と会話履歴の継続用途に限定する。

embedding可変化の制約: pgvectorは次元数混在を格納できるが、HNSW/IVFFlatインデックスは同一次元数の行にしか張れないため、次元数ごとに式インデックス+部分インデックスを用意する。インデックスの上限は2,000次元(halfvecなら4,000次元)。text-embedding-3-largeの3072次元は上限を超えるため、次元削減かhalfvecが必要。さらに異なるモデルのベクトルは比較できないため、テナントがembeddingモデルを変更した場合は全件再embeddingが要る。

Tenancy

マルチテナント構造

テナントの払い出しは管理者(開発者向け画面)のみが行う。ユーザー側でのテナント自己作成はできない。KBの認証情報はテナント本体とは別テーブル(tenant_kb_connections)に1対1で分離し、トークンはアプリ側で暗号化して保存する。

Notification

通知フロー

ラベルはKB側の機能をそのまま使い、ラベル付与をトリガーに通知を行う。宛先の解決はラベル→通知先のマッピングを管理設定画面で定義する方式。認証を最小構成としたためKBユーザーと本システムのアカウントを紐付ける土台がなく、assignee / ウォッチャーに従う方式は採れない。

Decisions

決定事項と残論点

要件を一問ずつ検証した結果、実装着手前に決めるべき論点は出揃った。以下は決定内容と、意図的に先送りした事項。

#論点決定状態
01会話履歴の永続化DBが正、localStorageはキャッシュ。端末跨ぎで継続可決定
02アカウント管理画面の範囲アカウント切替 + テナント読み取り表示 + 最低限のプロフィール編集決定
03KB認証情報のデータモデルtenant_kb_connections に分離、1対1、トークンは暗号化決定
04元メモの未確定点GitLabバージョン確認は破棄、残り3点を引き継ぎ決定
05認証方式独自認証は持たず管理者払い出しの識別子運用決定
06OCRテナント選択のLLMに委譲(固定プロバイダは設けない)決定
07embedding可変(テナント選択制)。次元数混在は部分インデックスで対応決定
08「ClaudeCode」の意味Claude API連携(CLI呼び出しではない)決定
09技術スタックPython + markitdown / TypeScript + React / PostgreSQL + pgvector決定
10差分更新cronポーリングに統一(Webhookは使わない)決定
11知識の実体KBが正、pgvectorは検索インデックス決定
12通知の宛先ラベル→宛先マッピングを管理設定画面で定義決定
13検索方式ハイブリッド。初期は類似度検索から、キーワード検索を後付け決定
—cronポーリングの実行間隔実運用の鮮度要求を見てから決定保留
—pgvectorのインデックス種別ivfflat / hnsw — データ量が見えてから決定保留
—ハイブリッド検索のマージ方式RRF等 — 両検索が動いてから実データで決定保留
—再embedding運用モデル変更時の手動/自動、実行中の検索の扱い保留
注意すべき前提: 決定05(認証を持たない)は社内クローズド運用を前提としている。インターネット公開する場合はこの前提が崩れ、独自認証またはIdP連携が後付けの改善ではなく着手時の必須要件になる。公開範囲が変わる際は必ず再検討すること。
